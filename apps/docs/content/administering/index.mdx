# Administering

This section is for the **Org Admin** — the person who holds the credentials and
decides what each Workspace can see. You reach all of it from **Organization
settings**.

A Workspace Owner composes things: Agents, Skills, Chats. You control what they
have to compose with. Anything carrying a credential, external reach, or code
execution — **Providers**, **MCP** servers, **Sandboxes** — is yours by default,
and you can hand some of it back per Workspace.

## Providers come first

A new installation has no Workspace and no **Provider**. Creating the first
Workspace asks for one: add it there, scoped to that Workspace, or first add a
Shared one here so the Workspace can attach it. Until a Shared Provider exists,
the Workspace form's **Shared provider** tab has nothing to offer.

Go to **Organization settings → Providers → Add provider**. A Provider created
here is available to every Workspace it's attached to; one created inside a
Workspace is private to it.

The Provider types, the form's fields, what each model needs declared about the
file types it accepts, and the guardrails field are all covered once in
[Providers & authentication](/self-hosting/providers-and-auth) — that page is the
Provider reference, and this section doesn't repeat it.

<Callout type="warning">
  A Provider is not visible to a Workspace merely because you created it at
  Organization scope. It has to be **attached** — see [Shared
  resources](/administering/shared-resources). A Workspace Owner reporting an
  empty **Model** dropdown after you "already set up the Provider" is usually a
  missing attachment.
</Callout>

## The screens

**Organization settings** holds:

| Screen               | For                                                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **General**          | The Organization's name, its identity / context text (folded into every Chat in the Org), and which Workspaces take [Inbound Trigger](#inbound-triggers) calls |
| **Members**          | Who is in the Organization, and their **Org Role**                                                                                                             |
| **Invitations**      | Inviting people in — see [Users & access](/self-hosting/users-and-access)                                                                                      |
| **Providers**        | The credential-bearing model connections                                                                                                                       |
| **MCP**              | Organization-scoped MCP servers                                                                                                                                |
| **Skills**           | Shared Skills, and where a promoted one is edited                                                                                                              |
| **Agents**           | Shared Agents, same                                                                                                                                            |
| **Blueprints**       | Named bundles of Shared resources you apply to a Workspace in one step                                                                                         |
| **Plugins**          | Read-only: what the deployment actually loaded at boot                                                                                                         |
| **Inbound Triggers** | Every Trigger in the Organization that an outside system can call, with its token's standing                                                                   |

### Members and roles

**Members** lists everyone in the Organization with their **Org Role**. A row's
menu offers **Edit org role** and **Remove from Org**.

A member with the `admin` role is an Org Admin — they can do everything on this
page, including to you. A **Super Admin** row is the platform-level account and
has no actions available here at all; an Org Admin can't change or remove it.

<Callout type="warning">
  **Remove from Org** doesn't touch the Workspaces that person owns. Their
  Triggers keep running as them, and their Inbound Trigger tokens stay valid.
  Revoke those tokens under [**Inbound Triggers**](#see-and-revoke) before you
  remove someone. Nobody can chat in their Workspaces afterwards, and since a
  Workspace's owner can't be reassigned, the only fix is to delete them.
</Callout>

<Callout type="info">
  **Plugins** is deliberately read-only — there is no install or enable button.
  Which Plugins run is a deploy-time decision belonging to the Operator, so it
  changes only when they edit configuration and restart. Use the screen to
  confirm what loaded, and to trace a Tool set or Sandbox backend back to the
  Plugin that provided it.
</Callout>

### Deleting the Organization

**General → Delete** asks you to type `Delete organization` to confirm. It
deletes every Workspace in the Organization, along with everything scoped to
them, and every Shared resource. Each Workspace's Sandbox is torn down too.
With the Docker backend that removes the container and its volume, so any files
an Agent left in `/workspace` are gone. With SSH the host is left alone. You
can't recover any of this from inside the product, only from a database backup.

## Inbound Triggers

An [Inbound Trigger](/building-with-platypus/triggers#inbound-triggers) is a
Trigger a system outside Platypus starts over HTTP, with a token its Workspace
Owner issues. Its run acts as that Owner, so it is a way in from outside, and
whether a Workspace may have that is your decision.

**General → Inbound Triggers** decides it for the whole Organization:

| Setting                 | Calls are accepted for                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Off** _(default)_     | No Workspace                                                                                                             |
| **All workspaces**      | Every Workspace, including ones created later                                                                            |
| **Selected workspaces** | Only Workspaces with **Allow Inbound Triggers** on in their [settings](/administering/workspaces#allow-inbound-triggers) |

It is checked on every call. Switching to **Off**, or turning a Workspace's
switch off under **Selected workspaces**, refuses that Workspace's calls from
the next one on. Its Triggers and their tokens stay as they are, so switching
back resumes them. Owners can create Inbound Triggers whatever the setting
says; they can't be called until you allow it.

<Callout type="warning">
  Switching from **All workspaces** to **Selected workspaces** stops every
  Workspace whose **Allow Inbound Triggers** switch is off, and every switch
  starts off. Turn it on in each Workspace that should keep taking calls first:
  the switch saves under any setting.
</Callout>

### See and revoke

**Organization settings → Inbound Triggers** lists every Inbound Trigger in the
Organization: its Workspace, Owner, when it was created, its **Token** standing
— **Active**, **Expiring soon** (within 30 days), **Expired** or **No token** —
and when it was **Last used** and **Last rejected**. It never shows a token.

**Last rejected** is the column to watch. A Trigger rejecting calls it used to
accept has lost its way in: an expired or revoked token, a **Disabled** badge,
or this Organization setting no longer admitting its Workspace. A Trigger
rejecting calls it never accepted may be someone guessing. It also moves when a
caller sends inputs that don't match the Trigger's, or when the server turns
calls away because it is already running as many inbound runs as it allows. The
[inbound call log](/reference/backend-configuration#the-inbound-call-log) names
the reason for each one. Both times update at most once a minute.

**Revoke token** stops a token at once and sends its Owner a notification. It is
the only thing you can do to another person's Trigger here. You cannot edit or
disable one.

<Callout type="warning">
  A revoke is not lasting: the Owner can issue a new token straight away. To
  stop a Workspace taking calls for good, change **General → Inbound Triggers**,
  which the Owner cannot.
</Callout>
